Для модульного/unit тестирования я использовал фреймворк Catch2.
Изначально подключил его как git сабмодуль:
    git submodule add https://github.com/catchorg/Catch2.git lab3/third_party/Catch2
когда пишешь git submodule add <url> <path>, git делает два дела:
    1) клонирует репозиторий Catch2 в указанную папку - в lab3/third_party/Catch2;
    2) + запись в .gitmodules чтобы Git + другие разработчики знали что это за подмодуль и откуда он берется.
мой .gitmodules:
    [submodule "lab3/third_party/Catch2"]
    	path = lab3/third_party/Catch2
    	url = https://github.com/catchorg/Catch2.git
    здесь написано:
        имя подмодуля
        path - куда клонирован локально Catch2
        url - откуда подмодуль был скачан

при сборке проекта Catch2 берется из локальной папки. В lab3/tests/CMakeLists.txt написано:
    add_subdirectory(${CMAKE_SOURCE_DIR}/third_party/Catch2 ...)
    то есть CMake подключает Catch2 как локальную директорию, сеть при сборке не нужна ибо все нужное уже лежит локально.

Чтобы не требовать от пользователя вручную инициализировать сабмодуль (как изначально делал я), добавлен скрипт
get_dependencies.sh который клонирует Catch2 в third_party/Catch2 только если:
    - папки еще нет
    - установлена переменная окружения WITH_TESTS
В CMakeLists.txt добавлен option(WITH_TESTS ...). Когда передаётся -DWITH_TESTS=ON,
CMake на этапе конфигурации вызывает скрипт через execute_process(), затем подключает тесты.
Таким образом достаточно одной команды cmake .. -DWITH_TESTS=ON и зависимости подтянутся сами.



Архитектура:
    Atom (что будет матчится с введенными строками):
        1) LiteralAtom - конкретный символ: 'a', 'B', '3', ' '
        2) AnyAtom - любой символ: '.'
        3) GroupAtom - набор/диапазон: [abc], [a-z]

    Token = Atom + Modifier (Once/Star/Plus/Question) - это пара "что матчить" + "сколько раз матчить это что-то"

    Regex = вектор токенов + рекурсивный матчер matchFrom()



Regex::Regex(const std::string& pattern)
    конструктор отвечает за парсинг шаблона регулярного выражения. Вызывается в main.cpp для например такого:
        Regex regex("a*[b-d]+")
        в рамках действия конструктора пользовательский шаблон разбивается на мои "токены": атомы и модификаторы и кладется в поле - вектор tokens.

    осуществляется проход по переданному по шаблону слева направо, на каждом шаге создается Atom:
        "[" -> GroupAtom,
        "." -> AnyAtom,
        иначе LiteralAtom).
        Затем в этом же шаге смотрится следующий символ: если это */+/?, то выставляется модификатор.
        Затем токен кладется в вектор токенов.

    Результат: вектор tokens заполнен.
    Пример: для паттерна "a*[b-d]+" в нем два токена: {LiteralAtom('a'), Star}, {GroupAtom("bcd"), Plus}.

std::string parseSet(const std::string& pattern, int& i):
    это вспомогательная функция которая вызывается когда парсер встречает "[";
    разворачивает содержимое строки "[...]" в строку символов. то есть "a-z" разворачивается в "abcde...z"

match(text) - точка входа которая просто зовет matchFrom(0, text, 0) - рекурсивный матчер.

bool Regex::matchFrom(int tokIdx, const std::string& text, int textIdx)
    Это рекурсивный матчинг шаблона и текста. метод принимает три параметра:
        1) tokIdx - какой токен по индексу сейчас рассматривается,
        2) text,
        3) textIdx - где в тексте нахожусь.

    if (tokIdx == tokens.size()) {
        return textIdx == text.size();
    }
    - это база рекурсии. вызывается когда все токены разобраны. если весь текст пройден то true.
    Далее берется текущий токен из вектора tokens и его атом.
    Затем смотрится модификатор:
        1) Once - один символ:
            if текст кончился ИЛИ символ не совпал → false;
            иначе рекурсия: следующий токен и следующий символ в тексте
        2) Star / Plus - жадные модификаторы:
            счет count: это счетчик который смотрит сколько символов исследуемого текста подряд совпадает с текущим атомом;
            при этом если модификатор атома Plus, то если count == 0 то выдаю false ибо нужен хотя бы один символ в тексте.
            Рекурсия заключается в том что беру следующий токен, а в тексте прыгаю на textIdx + count.
        3) Question - ленивый модификатор - сначала пробует взять в тексте 0 символов, потом 1:
             если matchFrom(tokIdx + 1, text, textIdx) - пропускаю 1 атом и сравниваю следующий с текущим символом в тексте;
             если не вышло:
                 если символ текста совпадает с атомом, то вызываю matchFrom(tokIdx + 1, text, textIdx + 1);
             иначе false.

    Пример 1: шаблон "a?a", текст "a". Первый атом {"a?"} берет 0 символов, а второй атом {"a"} берет символ "a" из текста.
    Пример 2: шаблон "a+", текст "aab":
        matchFrom(0, "aab", 0)
            токен {LiteralAtom('a'), Plus}
            count: 'a'==a ДА, 'a'==a ДА, 'b'==a НЕТ -> count = 2 -> textIdx += 2;
            matchFrom(1, "aab", textIdx=2)
                tokIdx == tokens.size() (1 == 1) значит срабатывает база рекурсии:
                textIdx == text.size()? <=> 2 == 3? НЕТ -> false
          -> "aab" не совпадает с "a+"

Как происходит автоматическое удаление полей у токенов?
1. Regex уничтожается (вызван delete явно или объект вышел из scope)
2. у Regex нет пользовательского деструктора -> компилятор генерирует его сам -> вызывает деструкторы всех членов,
    включая std::vector<Token> tokens
3. деструктор std::vector вызывает деструктор каждого своего элемента Token
4. у Token тоже нет пользовательского деструктора -> компилятор генерирует его сам -> вызывает деструкторы полей,
    включая std::unique_ptr<Atom> atom
5. деструктор unique_ptr<Atom> делает delete на хранимый указатель (Atom*), если он не nullptr
тут опять можно сказать про полиморфизм - статический указатель Atom*, а вот динамический (рантайм) - например GroupAtom*
    поэтому delete ptr здесь еще должно понять какой деструктор доч. класса вызывать:
    У меня ~Atom() виртуальный -> вызов деструктора идет через vtable и отработает ~GroupAtom() который удалит поле std::string chars;
    А если бы ~Atom() был бы НЕ виртуальным, то вызывался бы чисто ~Atom() (наверное). Для класса GroupAtom это утечка памяти.

можно сказать что std::unique_ptr<Atom> atom; это проявление концепции RAII:
    "владение ресурсом привязывается к времени жизни объекта":
    ~unique_ptr() который вызывается компилятором когда сам unique_ptr выходит из области видимости / уничтожается как
        часть уничтожения владеющего объекта (в моем случае поля Token, которое уничтожается как элемент
        std::vector<Token>, который уничтожается вместе с объектом класса Regex).

Система сборки в lab3:
Корневой lab3/CMakeLists.txt собирает две цели:
    1) regex_engine - статик либа (add_library(regex_engine STATIC regex_engine.cpp)
        target_include_directories(regex_engine PUBLIC
            $<BUILD_INTERFACE:${CMAKE_SOURCE_DIR}>
        )
        - "где искать заголовочный файлы для цели?"
        заголовки подключаются PUBLIC -> любая цель слинкованная с regex_engine получает путь до regex_engine.hpp.
        пути настроены только для этапа сборки проекта, разделяя логику сборки и установки библиотеки в систему.
    2) res - исполняемый файл (add_executable(res main.cpp)), линкуется с regex_engine через
        target_link_libraries(res PRIVATE regex_engine). PRIVATE означает, что зависимость от regex_engine -
        деталь реализации res, наружу (для того, кто линкуется с res) она не пробрасывается.
Это разделение нужно чтобы тесты могли линковаться с regex_engine не таща main() не нужный им.

Опциональная сборка тестов: option(WITH_TESTS ...)
    Если WITH_TESTS включен, то:
        execute_process(...) на этапе конфигурации (не сборки) запускает get_dependencies.sh,
            прокинув в него переменную окружения WITH_TESTS=1 через ${CMAKE_COMMAND} -E env
        enable_testing() включает поддержку CTest для этого проекта.
        add_subdirectory(tests) переходит в tests/ и выполняет там tests/CMakeLists.txt (Модульность)

    tests/CMakeLists.txt - сборка юнит-тестов
        Catch2 подключается не через find_package (не полагаюсь на то что Catch2 уже установлен в системе),
            а напрямую как поддиректория с исходниками (add_subdirectory); то есть Catch2 собирается вместе с проектом
            из исходников, а не берётся как пакет из системы.
            Второй аргумент - отдельная build-директория внутри CMAKE_BINARY_DIR чтобы не засорять дерево исходников.
        unit_tests линкуется с Catch2::Catch2WithMain (main() от Catch2 -> самому писать не нужно) И
            с regex_engine - тесты используют ту же скомпилированную библиотеку что и res.
        include(Catch) подключает CMake-модуль Catch2 с функцией catch_discover_tests, которая на этапе сборки запускает
            unit_tests --list-test-names-only
            и регистрирует каждый найденный тест как отдельный CTest тест.
